## 2. GitLab 工作流

### 分支

- `main`：可发布主分支，禁止直接 push。
- `feat/<module>-<short-name>`：新功能。
- `fix/<module>-<short-name>`：缺陷修复。
- `docs/<topic>`：文档和契约变更。
- `refactor/<module>-<short-name>`：不改变业务目标的重构。

### 开发流程

```text
同步 main → 创建分支 → 先写契约/任务 → 开发与测试
→ push → 创建 Merge Request → CI → Maintainer 审查
→ 合并 main → 通知相关模块 → 更新进度和文档
```

每次开发前必须同步最新 `main`。Merge Request 必须说明背景、改动、测试命令、影响模块、数据库迁移和回滚方式。

### 提交

使用 Conventional Commits：`feat`、`fix`、`docs`、`refactor`、`test`、`chore`。一次提交只解决一个清晰问题，不提交 `.env`、密钥、构建产物或个人临时文件。

## 3. 接口和代码规范

- 先改 OpenAPI / 共享类型，再写前后端实现。
- 跨插件通信使用 EventBus；禁止导入其他插件内部文件。
- 权限必须在后端接口校验，前端隐藏只作为体验优化。
- 数据库变更必须提供 migration，并在 MR 中说明旧数据兼容策略。
- 新页面必须说明空状态、加载状态、错误状态和无权限状态。
- 新功能至少补一条单元/接口测试；核心用户路径补 Playwright smoke。
- 文档中明确标注“已实现 / 开发中 / 计划 / 待决策”。

## 4. Definition of Ready

任务进入开发前必须具备：目标用户、页面入口、核心流程、验收条件、接口/数据影响、负责人和依赖项。只有一句“把某功能做出来”的任务不进入开发。

## 5. Definition of Done

任务完成必须满足：

- 代码已在功能分支完成并通过本地检查。
- API、共享类型、数据库迁移和文档同步。
- 有成功、无权限、异常或边界场景测试。
- MR 已经由 Maintainer 审查并合并。
- 能在统一环境演示，或明确记录阻塞原因。
- 项目进度表、风险清单和会议材料已更新。

## 8. 发布门禁

发布前必须执行：

```powershell
corepack pnpm typecheck
corepack pnpm run ci
corepack pnpm --filter @lab/web build
```

同时完成数据库迁移演练、核心账号登录、角色化看板、项目、物资、资料、会议和 AI 关键路径检查。任何密钥、外部服务地址和生产数据不得写入仓库。

## 9. 风险与应对

| 风险                  | 应对                                          |
| --------------------- | --------------------------------------------- |
| 需求继续膨胀          | v1.0 只承诺 P0，新增需求进入 P1/backlog       |
| 三组技术栈差异        | 只迁移能力和数据，不迁移独立运行时            |
| 跨模块互相等待        | 先定契约和 mock，插件并行开发                 |
| 动态字段过度复杂      | v1.0 只支持项目/物品的最小 JSONB 字段模型     |
| NAS/AI 外部依赖不稳定 | adapter + mock provider，保证平台主流程可运行 |
| 合并冲突和质量不一致  | 保护 main、强制 MR、CI 门禁、指定 Owner 审查  |
