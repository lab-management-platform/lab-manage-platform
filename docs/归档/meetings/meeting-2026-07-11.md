## 一、会议结论

### 1.1 整合方案确认

- **统一平台**：以常栋梁组的"实验室管理平台"为主干（React 19 + Fastify + PostgreSQL + 微内核插件架构）
- **统一入口**：唯一前端入口、唯一后端 API、统一数据库
- **废弃方案**：
  - 林钰滔组的 Spring Boot + MySQL 独立运行时，不再保留为生产依赖
  - 胡羿组的前端独立项目，不再保留为对外入口
  - SmartWrite-AI 的独立 Next.js 站点与 `/api/documents`，不再保留
- **吸收策略**：
  - 林钰滔组 → 编辑器能力 → 迁移为"项目笔记"插件
  - 胡羿组 → 审批流程设计 → 整合进"物资审批"流程
  - 两组 AI 能力 → 统一优化 AI 助手体验

### 1.2 技术路线确认

- 微内核 + 插件化架构（已实施）
- 插件间通过 EventBus 异步解耦，禁止跨插件直接导入
- 数据库使用独立 schema 或表前缀，禁止跨插件直接查表
- API 统一收口到 Fastify 宿主
- 前端统一 React 19 + TypeScript + Vite 6

## 二、功能需求全景

### 2.1 看板（Dashboard）— 第一优先级

用户入口为角色化看板，不同角色看到的内容不同。

**学生视角：**

- 我参与的项目及进展
- 我的待办任务
- 与我相关的资料/笔记
- 可申请的物资（含耗材、器材等）清单
- 我的物资借用记录
- 逾期未还提醒（首位展示）
- 近期会议安排

**组长/管理者视角：**

- 本组全部成员及项目分布
- 成员任务完成情况
- 物资（含耗材、器材等）库存总览
- 审批待办列表
- 成员参会/请假情况

**教师/管理员视角：**

- 全社人数统计（可按年度、分组筛选）
- 全社项目总览（按年度、等级、归属筛选）
- 物资（含耗材、器材等）总览（在库/在用/高值/低值/逾期）
- 会议/活动记录
- 日常工作开展情况

**架构要求：**

- 模块化、可动态扩展卡片
- 多级列表，可从总览下钻到明细（如：全社人数 → 某组 → 某人 → 其项目详情）
- 筛选维度可配置（年度、等级、归属等），字段不做死
- 支持横向交叉检索（如：从"成员维度"和"项目维度"都能定位同一条数据）

### 2.2 项目管理（Project）

**功能清单：**

1. 项目目录，支持多级筛选：
   - 一级：年份（2024 / 2025 / 2026）
   - 二级：项目等级（国家级/省级/校级/院级）
   - 或按进度筛选（立项/进行中/结项）
2. 项目详细视图：
   - 基本信息（名称、等级、负责人、成员、导师、时间）
   - 项目树（任务拆解、阶段目标）
   - 资料归档（文件、笔记、纪要、汇报）
   - 关联物资申请记录
   - 教师点评/审核入口
3. 进度工作台：
   - 进度卡片
   - 结构化汇报入口
   - 任务看板（可拖拽状态流转）

**架构要求：**

- 筛选字段可动态扩展
- 项目详情中的子模块以插件方式挂载

### 2.3 物资管理（Inventory / Equipment）

**学生视角：**

- 可申请物资（含耗材、器材等）清单浏览
- 在线申请（填写物品、数量、用途）
- 我的借用记录（时间、状态、应还日期）
- 我的历史申请
- 逾期提醒（前置展示）

**管理员视角：**

- 审批工作台（待审批/已审批/驳回）
- 库存总览：在库/在用，按分类（高值/低值、物资（含耗材、器材等））
- 借用追踪：谁借了什么、何时借出、应何时归还
- 逾期未还列表及提醒
- 物资（含耗材、器材等）存放位置

**架构要求：**

- 物品属性字段不做死（支持动态字段扩展）
- 字段可配置（字段名 + 字段值），支持数据库检索
- 与通知模块事件联动（申请提交 → 通知管理员审批）

### 2.4 文件资料 / 知识库（Knowledge Base）

- NAS 存储为底层数据支撑，平台作为前端口户
- 知识库为公共区域，全员可访问、查找
- 支持管理员上传/编写培训资料、学习资源
- 在线文档查阅（项目树、制度汇编等）
- 项目资料与知识库的逻辑衔接（项目结项资料可一键归档至知识库）

### 2.5 会议通知（Meeting / Notification）

- 会议安排与发布
- 参会确认 / 请假申请
- 会议纪要录入与关联
- 出勤统计
- 与看板联动（近期会议日程）

### 2.6 AI 助手（AI Assistant）

- 基于知识库的智能问答
- 项目资料上下文问答
- 可配置的 API 注入点（管理员可在后台填写 API 地址/Key）
- 支持云端 API 与本地推理切换
- 配套 Agent 扩展能力（未来）

### 2.7 权限体系（贯穿全部）

- 角色：学生 / 组长 / 导师 / 实验室管理员 / 平台管理员
- 不同角色在同一页面看到的内容不同（如物资页：学生看申请入口，管理员看审批入口）
- 权限控制贯穿前后端（前端 UI 级 + 后端接口级）

## 三、技术框架要求

### 3.1 架构原则

1. **模块化**：新需求以新插件方式添加，不修改核心
2. **动态可扩展**：插件可随时注册/激活/卸载
3. **数据隔离**：插件间不共享数据库 schema，通过事件通信
4. **字段不写死**：物资属性、项目字段等支持动态扩展

## 四、项目管理规范

### 4.1 Git 工作流

- **Main 分支**：常栋梁为 Maintainer，拥有合并权限
- **Feature 分支**：每个开发者从 main 拉取最新代码，创建 `feat/<模块名>-<功能>` 分支
- **开发前检查**：每次开发前 `git pull` 获取最新 main
- **合并流程**：Feature 分支 → Push → 创建 Merge Request → Maintainer 审查 → 合并
- **提交规范**：Conventional Commits（`feat:` / `fix:` / `docs:` / `refactor:` / `test:`）
- **CI 检查**：ESLint + TypeScript typecheck + Vitest + Build 全部通过方可合并

### 4.2 分工协作

- 每个插件模块独立开发，互不阻塞
- 接口契约（OpenAPI + TypeScript 类型）先于实现
- 跨模块依赖通过 EventBus 事件异步解耦
- 每周一次例会，同步进展、协调冲突

### 4.3 开发环境

- Docker Compose 一键启动
- 数据库迁移脚本统一管理
- 演示账号已就绪（admin / professor / student001）

## 会议后需求修订：物资管理

后续需求将原“耗材管理”升级为“物资管理”。物资是上位概念，首版至少包含耗材和器材，类别可以按实际需要扩展。

- 耗材：领用后默认消耗，不需要归还。
- 器材：按借用管理，必须归还，记录借用人、借出时间、应还时间、归还时间和逾期状态。
- 其他类别：通过类别配置决定是否需要归还，不能写死在页面代码中。
- `inventory` 技术插件名称暂时保留，但业务名称统一为“物资管理”。
