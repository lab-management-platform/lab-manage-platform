# 开发规范

版本：v1.0  
适用范围：所有主仓库开发成员、组长、维护者和联调人员

## 1. 协作角色

| 角色        | 责任                                       |
| ----------- | ------------------------------------------ |
| 主干维护者  | 维护 `main`、审查 MR、处理发布和跨模块冲突 |
| 模块 Owner  | 负责模块需求、接口、实现、测试、文档和演示 |
| 模块 Backup | 熟悉模块，协助审查和接替工作               |
| 贡献者      | 按任务开发、测试、提交 MR、更新进度        |

## 2. 任务进入开发前

每个任务必须写清楚用户、场景、页面入口、角色差异、成功/失败/无权限/边界情况、接口/数据库/事件影响、负责人、Backup、截止时间和验收条件。需求只停留在口头描述时不进入开发。新需求标记为 P0、P1 或待确认；影响数据库、权限或接口的变更必须同步正式文档。

## 3. GitLab 分支规范

| 分支                     | 用途                        | 示例                            |
| ------------------------ | --------------------------- | ------------------------------- |
| `main`                   | 可发布主分支，禁止直接 push | `main`                          |
| `feat/<模块>-<功能>`     | 新功能                      | `feat/projects-task-assignment` |
| `fix/<模块>-<问题>`      | 缺陷修复                    | `fix/inventory-return-status`   |
| `docs/<主题>`            | 文档、契约和 ER 图          | `docs/project-links`            |
| `refactor/<模块>-<功能>` | 结构重构                    | `refactor/projects-repository`  |
| `test/<模块>-<场景>`     | 测试补充                    | `test/projects-permission`      |

分支名使用英文小写、短横线和模块名；不要使用 `test1`、`tmp`、`new` 等无意义名称。

开发前同步主干：

```powershell
git switch main
git pull --ff-only origin main
git switch -c feat/projects-task-assignment
```

提交前执行：

```powershell
git fetch origin
git rebase origin/main
corepack pnpm typecheck
corepack pnpm run ci
```

冲突由提交者解决并重新检查，不得直接覆盖他人的修改。

## 4. 提交规范

格式：`<type>(<scope>): <简短说明>`。

允许的类型：`feat`、`fix`、`refactor`、`docs`、`test`、`chore`、`perf`。

示例：

```text
feat(projects): 支持项目负责人分配任务
fix(inventory): 修复器材归还后库存状态
docs(database): 更新项目链接字段和 ER 图
```

一次提交只解决一个主题；不得提交 `.env`、密码、API Key、构建产物、日志和本机配置。

## 5. Merge Request 规范

### MR 必填内容

- 背景、关联任务和改动范围。
- 影响模块、兼容性、权限变化和安全影响。
- 接口变化、数据库 migration、数据回填和回滚方式。
- 测试命令与结果；页面改动必须附截图或演示说明。
- 已知风险和未完成事项。

### 审核规则

- 至少一名模块 Owner 审核。
- 涉及 `core`、权限、数据库、公共契约或发布配置时，必须由主干维护者审核。
- CI 未通过、存在未解决评论或缺少 migration 时不得合并。
- 大 MR 拆成契约、数据库、后端、前端、测试等小 MR。
- 合并使用 Squash Merge，保持主干历史清晰。

审查顺序：需求匹配 → 权限正确 → 数据可回滚 → 接口兼容 → 错误状态 → 测试覆盖 → 文档同步。

## 6. 代码和模块规范

- `apps/web` 负责页面、布局、交互和路由，不直接访问数据库。
- `apps/api` 负责宿主装配、认证、路由和统一错误处理。
- `packages/core` 只提供认证、权限、事件、审计和插件契约，不放业务规则。
- `packages/contracts` 维护共享类型、OpenAPI 和稳定契约。
- `plugins/<模块>` 承载业务规则、数据访问、migration、事件和模块测试。
- 插件必须声明 ID、版本、依赖、权限、路由、事件、migration、配置和健康检查。
- 插件之间禁止直接导入对方内部实现，跨模块使用稳定 ID、API、领域服务或 EventBus。
- TypeScript 使用 camelCase/PascalCase；数据库使用 snake_case；API 使用复数资源名。

## 7. API 规范

1. 先更新需求、共享类型和 OpenAPI，再实现路由和页面。
2. 请求体、响应体、错误码、分页、筛选和排序必须有明确契约。
3. 后端必须校验登录、系统权限和项目内权限；前端隐藏按钮不是安全措施。
4. 项目接口必须校验项目归属；负责人、组长、普通成员和导师的边界不能只靠前端区分。
5. 创建任务、分配任务、提交进展、修改项目地址、物资审批和器材归还必须记录审计事件。
6. NAS、GitLab、AI Provider 通过适配器接入，错误信息不得泄露密钥。

## 8. 数据库和 migration 规范

数据库变更流程：

```text
更新数据库设计和 ER 图
→ 编写新增 migration
→ 设计默认值和数据回填
→ 本地执行并验证
→ 检查回滚/修复方案
→ 更新 API、类型、测试和文档
```

禁止修改已经进入共享环境的历史 migration。新增字段必须说明为空性、默认值、索引、唯一性、外键和回填方式。

当前重点字段：项目 `document_url`/`repository_url`；物资类别 `return_required`/`quantity_mode`/`serial_required`；申请 `consume`/`borrow`/`return`；项目角色 `owner`/`leader`/`member`/`advisor`/`observer`。

数据安全要求：密码和 API Key 不得明文提交；删除优先归档/软删除；跨模块只通过稳定 ID 或公开契约关联；生产数据不得进入公开截图、测试仓库或聊天记录。

## 9. 前端交互规范

每个页面必须处理加载中、空数据、错误、无权限和成功反馈五种状态。项目页面必须展示负责人、成员、项目文档地址和项目仓库地址；看板必须区分“我负责的项目”和“我参与的项目”。

## 10. 测试规范

必须覆盖：普通成员不能修改项目或分配任务；负责人可以分配任务；成员可以查看自己的任务并提交进展、资料和问题；教师可以查看和点评；项目地址为空/合法/非法时行为正确；耗材领用不生成归还任务；器材借用必须支持归还和逾期；未登录、非项目成员、负责人、教师、管理员权限边界正确。

检查命令：

```powershell
corepack pnpm typecheck
corepack pnpm run ci
corepack pnpm --filter @lab/web build
```

接口和数据库边界使用 Vitest/集成测试，核心用户路径使用 Playwright smoke。不得通过删除测试、跳过检查或降低断言解决失败。

## 11. 文档同步

产品需求、角色权限、接口字段、数据库表、ER 图、页面入口、开发计划或风险变化时，必须同步 `docs/项目文档/`。每个 MR 说明以下项目是否更新：

```text
[ ] 需求/功能
[ ] 角色权限
[ ] API/共享类型
[ ] 数据库/migration/ER 图
[ ] 测试
[ ] 部署/回滚说明
```

旧版文档只放在 `docs/归档/`，不作为新功能开发依据。

## 12. 发布、回滚和周会

发布前确认 CI、migration、演示账号、核心路径、外部链接、配置和回滚步骤。发布顺序：备份数据库 → 执行 migration → 部署 API → 部署 Web → 健康检查 → smoke → 记录版本和已知问题。失败时停止发布，先恢复服务或执行修复方案。

每周会议由模块 Owner 汇报：本周完成、可演示结果、下周计划、风险阻塞、需要老师决策的问题；会后更新进度、会议纪要和风险清单。

## 13. 新成员首日流程

```powershell
git clone <主仓库地址>
cd lab-management-platform
Copy-Item .env.example .env
corepack pnpm install
docker compose up --build -d
corepack pnpm typecheck
```

然后阅读[文档中心](./文档中心.md)，确认模块 Owner，启动项目，运行检查，领取一个小任务并提交第一个 MR。环境问题写入问题清单，不在个人机器上保留未说明的特殊配置。
