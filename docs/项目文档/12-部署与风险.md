# 部署与风险

## 1. 结论先说

当前项目具备 Docker Compose 部署骨架：开发环境可以按配置启动，生产环境有独立的 Compose 配置和 Nginx 镜像构建流程。但这不是“无需配置即可上线”的成品部署包。

可以部署的前提是：服务器已安装 Docker、Docker Compose、可访问镜像和依赖网络；已准备生产环境变量、数据库密码、JWT 密钥、AI/NAS 配置；已执行数据库迁移并完成健康检查。

## 2. 开发环境部署

### 前置条件

- Node.js 20.11+、pnpm 9+、Docker Desktop。
- 仓库依赖可安装，Docker 能拉取 `node:22-alpine` 和 `postgres:16-alpine`。
- 项目根目录存在 `.env`。

### 启动步骤

```powershell
Copy-Item .env.example .env
corepack pnpm install
docker compose config --quiet
docker compose up --build -d
docker compose ps
```

访问地址：

- Web：`http://localhost:5173`
- API：`http://localhost:3000`
- 健康检查：`http://localhost:3000/health`

开发 Compose 会启动 PostgreSQL、API 和 Web；PostgreSQL 健康后 API 才启动，API 启动后 Web 才启动。开发环境挂载源码目录，适合联调，不适合直接作为生产部署。

### 停止和日志

```powershell
docker compose logs -f api
docker compose logs -f web
docker compose logs -f postgres
docker compose down
```

## 3. 生产环境部署

### 3.1 准备配置

```powershell
Copy-Item .env.production.example .env.production
```

必须修改：

- `POSTGRES_PASSWORD`：强随机数据库密码。
- `DATABASE_URL`：与数据库用户名、密码、数据库名一致。
- `JWT_SECRET`：长度足够的随机密钥。
- `HTTP_PORT`：服务器暴露端口。
- `AI_PROVIDER` 和对应的 AI API/Ollama 配置。
- NAS 地址、账号和路径（如果启用 NAS）。
- `KEYCLOAK_ISSUER`、`KEYCLOAK_HOSTNAME`、`KEYCLOAK_CLIENT_ID` 和 Keycloak 管理员密码。

Keycloak 初始化模板位于 `infra/keycloak/realm-lab.json`。开发 Compose 会自动导入 `lab` Realm；生产部署前必须将 Realm 中的 `redirectUris` 和 `webOrigins` 从本地地址改为实际 HTTPS 域名，并重新检查 Web 客户端使用 PKCE、API 客户端为 bearer-only。Realm 导入不会替代用户创建和角色分配，正式成员应在 Keycloak 中创建并绑定 `lab_admin`、`professor` 或 `student` Realm 角色。

### Synology NAS 网络前提

本平台使用实验室的 Synology NAS 保存或承载资料文件。Synology NAS 不是公网存储，只有设备处于校园网内，或通过学校允许的校园 VPN 接入时，NAS 路径和 Synology Drive/共享链接才可访问。

- 部署服务器如果在校园网外，平台仍可启动，但 NAS 资料链接、NAS 文件索引和相关下载可能不可用。
- 开发电脑、API 服务器和需要访问 NAS 的浏览器都应确认已连接校园网或校园 VPN；只让浏览器连接校园网而 API 服务器在公网，不能保证后端索引任务正常。
- 不得把 NAS 管理端口、账号密码或内部共享路径直接暴露到公网；外部访问应通过学校 VPN、反向代理或经过审核的 Synology Drive 分享链接。
- NAS 不可达时，资料元数据仍可保留在平台中，但界面必须显示“当前网络无法访问 Synology NAS”，不能把不可达误判为文件丢失。
- 上线验收必须分别测试：校园网访问、校园 VPN 访问、非校园网访问时的降级提示，以及 NAS 恢复后的重新访问。

`.env.production` 不提交 Git，不放入前端构建产物，不通过群聊传递。

### 3.2 校验和构建

```powershell
docker compose -f docker-compose.prod.yml config --quiet
docker compose -f docker-compose.prod.yml build
```

生产配置使用 `api-prod` 和 `web-prod` 镜像：API 运行编译后的 Node.js 文件，Web 运行 Nginx 静态文件并把 `/api` 代理到 API 容器。

### 3.3 启动数据库和迁移

```powershell
docker compose -f docker-compose.prod.yml up -d postgres
docker compose -f docker-compose.prod.yml run --rm migrate
```

迁移成功后再启动 API 和 Web：

```powershell
docker compose -f docker-compose.prod.yml up -d api web
docker compose -f docker-compose.prod.yml ps
```

生产 Compose 中 `migrate` 使用 profile，不会随普通 `up -d` 自动执行，因此必须显式运行。数据库迁移失败时不得继续启动发布流程。

### 3.4 上线检查

```powershell
curl http://服务器地址/health
docker compose -f docker-compose.prod.yml logs --tail=100 api
docker compose -f docker-compose.prod.yml logs --tail=100 web
```

检查登录、项目列表、项目详情、任务分配、进度提交、物资申请、会议页面和 AI 配置。确认 Nginx 的 `/api/` 代理、SSE 事件流和前端路由正常。

## 4. 当前验证结论

- 开发 Compose 配置：已通过 `docker compose config --quiet` 语法校验。
- 生产 Compose 配置：在提供 `POSTGRES_PASSWORD` 后通过配置校验。
- Dockerfile：包含开发、API 生产和 Web 生产构建阶段。
- 实际镜像构建、数据库迁移、服务器域名、HTTPS、Synology NAS 校园网/VPN 连通性和 AI 连通性：尚未在目标服务器完成现场验证。

## 5. 回滚流程

1. 发布前备份 PostgreSQL 数据卷或数据库备份文件。
2. 记录当前镜像版本、Git commit 和 migration 状态。
3. Web/API 发布异常时，回退到上一个镜像版本。
4. 数据库 migration 失败时停止发布，按对应 migration 的修复方案处理；禁止直接删除生产数据或执行未经审核的降级 SQL。
5. 恢复后重新执行健康检查和核心业务 smoke。

## 6. 主要风险

- **配置风险**：生产 `.env.production` 未配置或密钥过弱会导致启动失败或安全事故。
- **迁移风险**：目标数据库设计已增加项目链接字段、物资类别和归还规则，实际 migration 尚未全部实施。
- **外部依赖风险**：Synology NAS、AI Provider、镜像仓库和服务器网络不可用时，相关功能会降级或失败；NAS 还额外依赖校园网或校园 VPN。
- **数据风险**：当前演示账号和种子数据只适合开发环境，生产必须关闭 `LAB_SEED_DEMO_ACCOUNTS` 并准备正式账号。
- **运维风险**：当前 Compose 未提供完整的 HTTPS、备份、监控、告警和自动发布能力，需要由部署环境补齐。
- **版本风险**：数据库迁移、API、Web 必须来自同一 Git commit，不能混用不同版本的镜像。

## 7. 是否可以上线

结论：**可以作为开发环境和测试环境部署；生产上线还需要完成环境配置、数据库 migration、备份、HTTPS、外部服务连通性和核心流程验收。**

因此，当前更准确的状态是“可部署骨架 + 待完成生产化准备”，不是已经验证过的生产发布包。
