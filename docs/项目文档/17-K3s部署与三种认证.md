# K3s 部署与三种认证

## 1. 部署方式

开发环境继续使用 Docker Compose；生产环境使用 K3s：

- `deploy/k3s/`：Namespace、PostgreSQL、Keycloak、API、Web、Ingress。
- GitHub Actions 构建 API/Web 镜像并推送到 GHCR。
- 流水线通过 SSH 在 K3s 节点执行 `kubectl apply -k deploy/k3s`，再滚动更新镜像。
- 证书使用 K3s Secret `lab-wuosu-tls`，由集群 Ingress 使用；不把私钥提交到仓库。
- `secret.example.yaml` 只是字段模板，正式部署由流水线 Secrets 生成 Secret。

必须配置的 GitHub Secrets：

`K3S_HOST`、`K3S_USER`、`K3S_SSH_PRIVATE_KEY`、`GHCR_PULL_TOKEN`、`K3S_POSTGRES_PASSWORD`、`K3S_KEYCLOAK_ADMIN_PASSWORD`。

## 2. 三种认证的关系

平台不维护三套互相独立的用户。Keycloak 是正式身份中心，平台数据库保存业务资料和审核状态。

1. Keycloak 统一登录：正式成员通过 OIDC 登录。
2. 管理员创建账号：用于已有成员导入和迁移阶段；生产过渡期可使用平台账号登录。
3. 个人注册申请：任何人只能提交 `pending` 申请，不能直接登录；管理员审核通过后激活账号，并在后续同步到 Keycloak。

生产环境建议使用 `AUTH_MODE=hybrid`：同时兼容 Keycloak 和本地账号。迁移完成后切换为 `AUTH_MODE=oidc`，关闭本地密码入口。

当前已完成：

- 个人注册申请接口：`POST /auth/registration`。
- 管理员查看待审申请：`GET /auth/registrations/pending`。
- 管理员审核申请：`PATCH /auth/registrations/:id`，`action=approve|reject`。
- 未审核账号不能使用本地密码登录。
- 审核状态、审核人、审核时间、驳回原因均写入数据库。

后续必须补充：审核通过后通过 Keycloak Admin API 自动创建/绑定用户，并把 Keycloak `sub` 写入 `external_subject`；完成迁移后关闭本地密码登录。
