# 跨组整合总说明（真实落地版）

适用对象：整合开发负责人、后端/前端联调成员、数据库设计成员  
更新时间：2026-07-08  
关联文档：[跨组整合专题入口](./README.md) · [数据库设计](../03-data/database-design.md) · [API 总览](../04-api/api-overview.md)

## 目标

以当前实验室管理平台仓库为主干，吸收其他小组的模块能力，形成统一的实验室协作平台，而不是把多个独立前端简单拼接到一起。

整合后的主线仍保持：

- 项目管理是核心入口
- 项目驱动耗材、文件资料、会议通知、AI 助手和知识沉淀
- 身份、权限、项目归属、消息机制、文件结构、AI 上下文由本仓库统一治理

## 为什么前端暂时没有明显变化

当前阶段的重心不是重新出一套新皮肤，而是先做三件真正决定能否整合成功的事：

1. 明确每组模块的真实边界
2. 对齐数据结构和接口口径
3. 决定哪些能力保留为独立模块，哪些吸收到现有页面

因此短期内可以保持“前端壳层基本不变”，但后台的数据流、模块入口和页面内部能力会逐步替换。

## 统一整合原则

### 1. 前端壳层统一

- 使用本仓库 `apps/web` 作为统一工作台
- 保留统一登录、统一项目选择、统一消息入口、统一角色展示
- 其他组的功能以页面模块、子视图或卡片入口形式接入

### 2. 后端主干统一

- 使用本仓库 `apps/api + plugins/*` 作为主干
- 新接入能力优先做成插件或插件内子模块
- 不直接把其他仓库的前后端整体搬入生产主线

### 3. 数据归一

- 身份主线以 `identityType + identityNo` 为准
- 项目主线以 `project` 为核心对象
- 文件、通知、会议、知识库、项目树等都要能绑定项目或全局作用域

### 4. 权限归一

- 统一角色：`student / professor / lab_admin / member / admin / super_admin`
- 统一项目内成员角色：`owner / leader / member / advisor / observer`
- 任何新模块都不得绕开现有认证与项目权限模型

## 三组功能的整合定位

### 本组：实验室管理平台

- 提供统一工作台
- 提供项目主线、权限、会议通知、资料管理、项目树、结构化汇报、AI 助手
- 作为最终整合后的主仓库

### SmartWrite-AI：笔记/写作组

- 不作为独立站点保留
- 可沉淀为：
  - 项目笔记
  - 知识卡片
  - 会议纪要草稿
  - AI 写作辅助上下文
  - 阶段汇报文本编辑

### tech-material：完整管理台组

- 不作为“单一耗材模块”处理
- 本质上是一套独立的 `Spring Boot + Vue` 管理平台
- 优先拆解并迁移：
  - 耗材、出入库、盘点、申请审批
  - 项目、任务、成员
  - 公告、通知、会议
  - 文件管理与知识文档

## 数据库整合策略

### 主仓库保留的数据核心

- `core`：账户、会话、审计、迁移
- `projects`：项目、成员、任务、项目树、快照、汇报
- `files`：项目资料、版本、外链/NAS 路径
- `collaboration`：会议、通知、公告、已读
- `inventory`：耗材、申请、审批、流水
- `ai`：知识文档、问答上下文、FAQ

### SmartWrite-AI 的推荐落点

- 原“文档实体”不要独立成为平行主表体系
- 推荐映射为：
  - `ai.knowledge_document` 或知识库相关表：面向通用知识沉淀
  - `files.lab_file + file_version`：面向附件、导出稿、资料版本
  - `projects.project_report`：面向阶段性正式汇报文本
  - 如确需保留编辑中草稿，再新增 `projects.project_note` 或 `ai.note_document`

### tech-material 的推荐落点

- `inventory`：吸收 `material / stock_record / inventory_check / application`
- `projects`：吸收 `project / project_member / task / task_comment`
- `collaboration`：吸收 `meeting / announcement / notification`
- `files`：吸收 `file_record / file_folder`
- `ai`：吸收 `knowledge_doc / qa_conversation`
- 若对方有独特字段，优先扩展本仓库表，而不是保留平行系统表

## API 对接策略

### 总体原则

- UI 最终只调用本仓库 API
- 其他组接口不直接暴露给最终前端
- 若复用他组逻辑，应在主仓库 API 层完成适配与封装

### SmartWrite-AI

- 可复用其编辑器组件思路
- 不建议复用其 `/api/documents` 路由原型
- 原因：
  - 认证方式不同
  - 默认文件系统存储
  - 缺少项目权限和实验室角色语义

### tech-material

- 可作为完整业务流程与接口对照清单
- 真正对接时必须收敛到本仓库各插件的统一路由
- 不保留外部 `Spring Boot` 路由作为最终前端依赖

## 前端整合策略

### 统一不变部分

- 统一顶部项目上下文
- 统一左侧导航
- 统一角色展示和消息入口
- 统一登录工作台

### 逐步接入部分

- 笔记/知识功能接入 `AI 助手` 或 `文件资料` 的子页签
- 耗材功能继续归在 `耗材管理`
- `tech-material` 拆出的能力分别挂到：
  - `项目管理`
  - `耗材管理`
  - `文件资料`
  - `会议通知`
  - `AI 助手`

## 当前阶段建议产出

本周内建议至少形成：

1. 各组真实功能边界清单
2. 统一身份与权限映射表
3. 数据表映射草案
4. API 收口清单
5. 页面入口草图
6. `SmartWrite-AI` 与 `tech-material` 的字段/接口收口矩阵

## 风险

- 其他组如果直接以独立站思维开发，后续整合成本会很高
- `SmartWrite-AI` 当前默认文件系统存储，不适合直接进统一生产架构
- `tech-material` 当前带有硬编码数据库配置和过粗角色模型，不能直接接入
- 如果先改 UI 再对齐模型，后续返工会很多

## 当前建议对外表述

可以对外说：

- 已经明确采用“本仓库做统一工作台、其他组能力按模块并入”的整合路线
- 当前正在做模块边界、数据模型和接口口径的对齐
- 前端外观暂未大改，是因为本阶段先确保功能能在统一架构下落地

不建议对外说：

- “已经全部联调完成”
- “整合后的完整界面已经定稿”
- “三组代码已经全部并到一起”
